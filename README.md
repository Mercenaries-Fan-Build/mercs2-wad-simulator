# mercs2-wad-simulator

A Rust workspace for Mercenaries 2 WAD analysis, asset extraction, and Xbox-to-PC conversion.

## Binaries

### `qm` — the Quartermaster
Lints and builds **Shipments**: the mod package format (a `manifest.yaml` plus a `src/` directory).
This is the tool a *mod author* uses; everything else here is for analysing and converting game data.

```bash
qm lint  ./my-shipment                  # check it — no game install needed
qm build ./my-shipment --out build      # produce the overlay WAD
qm link  ./mod-a ./mod-b --out deploy   # compose several mods' Lua into one WAD
qm rules                                # every check, and the ones not implemented yet
```

`qm lint` is hermetic — manifest text plus the Shipment directory, no game and no network — which is
what lets it run in a public CI job. `qm build` and `qm link` need the retail WADs.

Gated on the **exit code**: `0` clean, `1` findings at error or above, `2` could not run at all.

Start from the [Shipment template](https://github.com/Mercenaries-Fan-Build/mercs2-shipment-template),
which has a runnable example for every contribution kind.

### `wad_simulator`
Engine-accurate consumption simulator for WAD archives. Validates WAD structure, detects out-of-bounds ASET entries, and runs every asset through a consumption pipeline (meshes, textures, sounds, scripts, etc.). Useful for validating WAD conversions and catching data corruption before runtime.

```bash
wad_simulator --wad output/data/vz-patch.wad --rainbow-table tools/rainbow_table.json
```

### `ucfx_byteswap`
Converts Xbox 360 (big-endian) UCFX blocks to PC (little-endian) format. Used in the DLC Xbox-to-PC porting pipeline. Handles entire asset blocks with full struct-aware byte-swapping.

```bash
ucfx_byteswap /path/to/xbox_block.bin --output /path/to/pc_block.bin
```

### `loadprobe`
Analyzes `pmc_blackbox.log` from game runs to quantify world-load progress and classify end-state (crashed, hung, or fully loaded). Scores against a 21-phase milestone ladder and surfaces diagnostics.

```bash
loadprobe /path/to/pmc_blackbox.log
```

### `exemap`
Identifies a `Mercenaries2.exe` build by sha256 and checks it against its code layout: every byte
that differs from the layout's reference build must be a catalogued overlay
(`crates/mercs2_exemap/data/*.tsv`). Exit status 0 on a member, 1 on an unknown build or an
unlisted difference, 2 when a file cannot be read.

The code layouts are the code versions of the game. `U` (PE timestamp `0x48a370c7`) is
v1.0: the archived disk dump `archived-2-disk-dump`, the archived cracked build
`archived-1-cracked-cruise`, and every other cracked, DRM-free and SecuROM-unwrapped build in the
catalogue. `E` (PE timestamp `0x48cae190`) holds `v10-ea-signed`, the EA-signed release, and
`v11-patched-securom`, which the official v1.1 patcher (sha256 `b27fedc2…`, one file for all four
regions) writes from `v10-ea-signed`.
`D` (PE timestamp `0x48cb59e8`, 13 Sep 2008) is the PC demo: `demo-official-securom`, the
`Merc2-Demo.exe` that `Mercs2_Demo_Setup.exe` extracts, wrapped like the retail files.
`builds.tsv` records each build's `code_version`; `aliases.tsv` maps other ids for a build,
including the ones Modkit uses, to its canonical id, and `identify` prints the canonical id.

Every table under `crates/mercs2_exemap/data/` is tab-separated with one exact header line, and no
field is empty: a column with no value holds `-` (a build with no recipe or no overlay set, an
overlay row with no `detail`, an image with no `build_id`, `code_image` or chain, a corpus that
applies to nothing, a WAD with no chain or no `install` key). An empty field fails the parse with
an error naming the table, line and column, and `-` in a column that must hold a value fails it
too. No command writes these tables; `xbox_exports.tsv` and `ps3_fnid_names.tsv` are generated by
`crates/mercs2_exemap/tools/import_names.py` (see `exemap imports`), the rest are edited by hand.

```bash
exemap identify Mercenaries2.exe
exemap check Mercenaries2.exe --reference <layout-reference.exe>
```

It also takes in the console executables for disassembly:

- `exemap xex <xex> --key retail|devkit --out <pe>` recovers the PE image from an Xbox 360 XEX2
  file: it unwraps the session key with the named key-encryption key, decrypts the basefile and
  undoes its compression (LZX through `mercs2_formats::lzx`). A key that does not fit the file is
  an error naming the key.
- `exemap ghidra-pe <pe> --out <pe>` rewrites an Xbox 360 image's section headers to its RVA
  layout.
- `exemap starts <image> --out <list>` writes one hex VA per line: the `.pdata` starts of an Xbox
  360 PE (every executable section, `.text` and `BINK`), or the `.opd` descriptor code addresses of
  a PS3 PPU ELF (found from the entry descriptor). The list seeds Ghidra's `CreateFunctions.java`.
- `exemap imports <image_id> --from <container> --exports <dir>` rebuilds an `images.tsv` console
  image and writes `<dir>/<image_id>.imports.tsv`, the imports sidecar `FnMnemonicSig.java` reads;
  its header names the format. An Xbox 360 image (a chain with an `xex:` step) gets one row per XEX
  import record, `address kind library ordinal name`: the record's address, `function` (a 16-byte
  loader stub ending `mtctr r11; bctr`) or `variable` (an import slot), the library, the ordinal and
  Xenia's name for it (`data/xbox_exports.tsv`). A PS3 image (a chain ending in its `unself:` step)
  gets one row per PRX function import, `address kind library fnid name stub`: the 32-byte code
  stub, the library, the FNID as 8 hex digits, a name that hashes to that FNID (the first 4 bytes,
  little-endian, of SHA-1 of the name followed by the 16 bytes
  `67 59 65 99 04 25 04 90 56 64 27 49 94 89 74 1A`, checked when `data/ps3_fnid_names.tsv` loads) or
  a module-level NID from `data/ps3_fixed_nids.tsv`, and the stub's bytes. Every record is checked
  against the image (the record word or stub pattern, and one import-table entry per stub); a
  mismatch, an import with no name, or a PS3 library with variable or TLS imports is an error. PS3
  v1.00 imports 227 functions from 17 libraries, v1.03 235 from 18; the Xbox 360 images 531–535
  records. `tools/import_names.py` generates `xbox_exports.tsv` from Xenia's export tables and
  `ps3_fnid_names.tsv` from RPCS3 and Ps3GhidraScripts' `nids.txt`; those tables and
  `ps3_fixed_nids.tsv` start with `#` lines giving their provenance before the header.

```bash
exemap xex mercs2_xenon_p_EN_FR.xex --key devkit --out profile.pe
exemap ghidra-pe profile.pe --out profile.pe_ghidra
exemap starts profile.pe_ghidra --out profile.starts
```

`crates/mercs2_exemap/data/images.tsv` lists the images the function map spans on every platform,
each with the Ghidra language and load base it is analysed with. Each PC row names its build id:
`pc-v10` and `pc-v11` are the two layout references' SecuROM-unwrapped process dumps
(`dump-v10-pmcbb-unpacked`, `dump-v11-securom-unpacked`), and `pc-v10-drmfree` is the DRM-free
v1.0 executable `v10-drmfree-laa` (`mercs2_nodrm_v3.exe`), which
`securom_unwrap::unwrap` builds from `v10-cracked-pmcbb` with the large-address-aware flag set. It
has no `code_image`; the `pc-v10` dump differs from it by three `.text` hot-patches and runtime
bytes in `.securom` (`overlays.tsv`). Each console row carries the chain that
rebuilds it from its original container (a file from the Xbox disc, `xex`, `ghidra-pe`; a PSN
package entry, `unself`), and `exemap derive` replays it, checking every sha256 on the way. A
regional build whose executable sections and function starts match another image byte for byte
names that image as its `code_image` (the PS3 v1.03 EU and DE EBOOTs share the NA code and differ
only in their embedded region config). The PS3 regional disc EBOOTs are mapped too: `ps3-v100-jp`
(BLJM60101, APP_VER 01.00, its own code), and `ps3-v101-eu` (BLES00323, APP_VER 01.01) with
`ps3-v101-de` (BLES00328), which shares its code byte for byte. Each is rebuilt with `unself:app`
from `<disc dir>/PS3_GAME/USRDIR/EBOOT.BIN`, found through the `ps3_jp_disc_dir`, `ps3_eu_disc_dir`
and `ps3_de_disc_dir` keys.

`exemap rtti <image> --out <tsv>` recovers vtables from an image's own C++ type information and
writes one row per slot (ABI, decorated name, `Foo::Bar` class name, vtable address, subobject
offset, slot index, function address): MSVC locators in the PC and Xbox 360 PEs (both byte orders),
GCC/Itanium typeinfo in the PS3 ELFs, where each slot is an `.opd` descriptor resolved to its code.
The PC and Xbox images carry type information for about 270 classes (mostly Havok); the PS3 images
for about 1,290, game classes included. Xbox 360 `.pdata` omits leaf functions, so about half of
the Xbox slots point at functions that have no `.pdata` entry. Each MSVC row also names its vtable's
destructor slot, the one slot whose function tests the deleting-destructor flag (PowerPC: `r4 & 1`;
x86: the first stack argument `& 1`, followed through the stack depth); GCC gives that destructor
two slots, so a PS3 vtable of the same class has one slot more.

`exemap luareg <image> --out <tsv>` recovers the Lua C-function registration tables (`luaL_Reg`
arrays of `{name, function}` ended by `{NULL, NULL}`) and writes one row per entry. The game's
tables nest groups with marker entries, `{name, 0xFFFFFFFF}` to open and `{name, 0xFFFFFFFE}` to
close, so `Graphics` holds `Camera.SetNearFar`. A table's namespace is the `name` of the registry
row that points at it. The registry is an array of 12-byte rows `{const char* name, luaL_Reg*
table, const char* init}`: each row's `table` word points at a recovered table, its `name` word
holds an identifier, and its `init` word is 0 or points at NUL-terminated text. Only rows in a run
of at least two consecutive rows name a table; a lone `{name, table}` word pair names nothing. The
PC images name 31 namespaces holding 1,081 bindings, and the Xbox 360 Final and retail images 30,
as data. The Xbox 360 Profile image and the PS3 images leave each row's `name` and `init` words zero
in their bytes and write them from code: a static initializer (PS3 `0x0050a8e8`, Profile
`0x829eba98`) copies each library's `const char*` name into its row. On PowerPC images `luareg`
evaluates every function's constant-address `stw` stores over its control flow and takes the words
from those stores, so those images name the same 30 game namespaces. No image has a registry row
for the Lua libraries (`_G`, `coroutine`, `string`, `table`), so those tables are unnamed on every
platform.

`crates/mercs2_exemap/data/corpora.tsv` catalogues the Lua corpus by product (`base`, `demo`,
`patch`, `dlc:<name>`), platform and build, a patch or DLC naming the corpus it applies to;
scripts are compared only within one product. `wads.tsv` lists each corpus WAD by sha256 with the
chain that rebuilds it from the original file: `zip:<entry>`, `xdvdfs:<path>` (a file from an Xbox disc image), `stfs:<name>` (a file from an Xbox 360 STFS
package), `iso9660:<path>` (a file from an ISO-9660 disc image, read through its Joliet tree),
`pkg:<path>` (an entry of a PSN `.pkg`) and `edat:<klicensee>` (an NPDRM EDAT's payload, decrypted
with the 32-hex-digit title klicensee once it validates against the EDAT header). A WAD's name is
its path from the install or disc root (`data/vz.wad` on PC, `vz.wad` on Xbox 360,
`PS3_GAME/USRDIR/VZ.WAD` on PS3), or its path in its package for a patch or DLC. The Xbox 360 corpora are the Jul 11 2008
preview disc, the retail disc dump, and the Blow It Up Again Pack (retail, the Nov 6 and Nov 25
2008 prototypes, and the Pack B prototype) and Amazon Pack prototype packages, each DLC's script
archive being its `.doh`. The PS3 corpora are the North American disc BLUS30056 (a community-assembled ISO
whose primary and Joliet trees both list VZ.WAD's final extent out of order; see the `iso9660`
module), its v1.03 update (`VZ-PATCH.WAD` and `SHELL-PATCH.WAD`), and the Blow It Up Again Pack
(`DLC01.EDAT`, decrypted with the klicensee recovered from the v1.03 EBOOT). The Japanese disc BLJM60101, the German disc
BLES00328 and the European disc BLES00323 (both application version 01.01) are decrypted folder
dumps, their WADs checked in place; the European disc shares its English, German, Loading, shell
and vz WADs with the German one. Each of the three v1.03 updates is catalogued against its own
region's disc; the German update ships the same patch WADs as the North American one, the European
update its own.
`exemap corpus-derive` replays one chain, checking every sha256. A WAD with no chain (`-` in
`from_sha256` and `step`) is catalogued from an install: its `install` column is either the
local-config key of the install directory, or `canonical:<dir>`, a directory under the
`canonical_dir` key's canonical tree of PC builds. Every PC corpus is catalogued from that tree:
- `base-pc-demo` from the demo install (`canonical:demo`); its executable is build
  `demo-official-securom`, layout `D`;
- `base-pc-retail`: English, Loading, shell and vz from the v1.0 EA-signed install
  (`canonical:Mercenaries 2 World in Flames`, executable `v10-ea-signed`), byte-identical to EA's
  download manager install, plus French, German, Italian and Spanish from the ElAmigos repack
  (`canonical:repack-languages`);
- `base-pc-elamigos`, the repack itself (not official media), installed once per language with
  English last: its English, shell and vz are byte-identical to the official ones, and its
  Loading.wad (in `canonical:repack-languages`) differs from the official one (and the demo's) only
  in a 20-byte identifier string at `0x8271`. It ships the v1.1 executable `v11-patched-securom`.

```bash
exemap corpus-derive base-x360-preview vz.wad --from "Mercenaries 2 Preview X360 (Jul 11 2008).iso" --work /tmp/preview
```

`exemap lua-scripts <wad> [--dump <dir>]` lists every Lua script container of a WAD on any platform,
one row per container: its block, entry, name hash, script name (from the INFO record), function and
instruction counts, whether the chunk keeps debug information, block path, and each descriptor's tag
and size; `--dump` also writes each descriptor body to a file. Scripts are found by their entry
type in every block. Each container's checksum is verified; the
one exception is the last container of a block stored uncompressed (every block of the Japanese PS3
disc), whose trailer is eight zero bytes. Every chunk is decoded (`luachunk`: Lua 5.1, little-endian
on PC, big-endian on console) and must re-encode to its exact bytes, or the command fails. The
retail counts are 645 (vz) + 28 (shell) scripts on PC and 643 + 26 on Xbox 360 and every PS3 disc.
PC and the Japanese PS3 disc keep their debug information (line info, local and upvalue names); the
Xbox 360 and the European and German PS3 discs strip it.

`exemap lua-index <corpus_id> --wad <file>... --out <tsv>` writes one row per Lua function of a
corpus. Each file must match a `wads.tsv` WAD of that corpus by sha256, and every WAD of the corpus
must be given; a WAD rebuilt from a container comes from `exemap corpus-derive`. A row carries the
WAD, script name and name hash, the function's `path` in its script (`main`, then `/<i>` per nesting
level), its line range, parameter/vararg/upvalue/stack shape, code, constant and nested-function
counts, and two platform-neutral fingerprints: `code_hash` (SHA-256 of the instruction words,
little-endian) and `constants_hash`; `debug` says whether it keeps debug information; `lookups`
lists every `Namespace.Name` the function reads the way Lua 5.1 compiles it (`GETGLOBAL` immediately
followed by `GETTABLE` with a string-constant key) — a function about to be called, or any other
field such as an event id or a sub-table.

`exemap lua-pair <a.tsv> <b.tsv> --out <tsv>` pairs the functions of two `lua-index` exports by
content. Scripts pair by name hash (a script that several WADs of one corpus carry with the same
code counts once). Inside a script the two main functions pair, then every function whose code and
constants fingerprints are unique on both sides, then the nested functions of each pair are aligned
in order along a longest common subsequence of their code fingerprints; equal-length runs between
aligned children pair in order.
Each pair is `identical`, `identical-debug-differs` (one side strips debug information),
`constants-differ` or `code-differs`; every other function is `only-a`/`only-b` and every other
script `script-only-a`/`script-only-b`. Across the retail builds, the PC and Japanese PS3 scripts
are one revision (6,221 functions identical, 57 with different code) and the Xbox 360, European and
German PS3 scripts another (6,297 identical between Xbox 360 and Europe, one different); the two
revisions differ in about 1,000 functions.

`exemap lua-link <index.tsv> <image.luareg.tsv> --out <tsv>` resolves every lookup of a `lua-index`
export through an image's `luareg` export, by namespace and entry name: `resolved` (one native
function), `ambiguous` (several), `unregistered-in-native-namespace` (the namespace is registered
natively, the name is not — mostly event ids, constants and sub-tables) or `lua-namespace` (no
native table carries that namespace: a table the scripts build themselves). The command prints how
many namespaces the export names and refuses an export that names none. Each retail script set resolves about 660–680 distinct lookups
to native functions (PC 719 against `pc-v11`, Xbox 360 664, the PS3 discs 676–677).

`cargo xtask retail-test` checks these results: `tests/lua_corpus.rs` indexes every catalogued
corpus (every chunk decodes and re-encodes), checks each corpus's function and script counts, the
pairing counts of the same-lineage corpora, and the PC and Xbox 360 retail lookup links computed
from the `pc-v11` and `x360-retail` images' registration tables.

`exemap match <image_a> <image_b> --exports <dir> --evidence <list> --out <tsv> --conflicts <tsv>`
pairs the functions of two `images.tsv` images from their exports in `<dir>` (`<id>.rtti.tsv`,
`<id>.luareg.tsv`, and `<id>.fnsig.json` from `FnMnemonicSig.java` for the signature evidence).
Every rule is an identity or uniqueness test: `vtable` (same class, vtable ordinal and slot, only
where both images give the class the same vtable count and each vtable pair the same slot count, or
an MSVC vtable with a recognised destructor slot against a GCC one with one slot more, aligned
around the destructor, which itself stays unpaired), `lua` (same namespace and
binding, or a binding name unique in each image), `bytes` (a masked-bytes hash unique in each
image), `string` (a string referenced by exactly one function in each image) and `callee`
(positional callees of accepted pairs whose call lists agree with every accepted pair). `bytes`
and `callee` apply only between images analysed with the same Ghidra language. `callee` pairs only direct callees that are function starts (keys of
each image's fnsig export). Two aligned call-list entries agree when both are imports
(`ext:<library>!<name>`) with exactly the same library and name, both are PS3 system calls
(`sys:<N>`) with the same number, or both are indirect (`*0x…` a call through a memory slot,
`*stack:<signed hex>` through a function pointer in a stack variable, `?` a computed target)
whatever their operand; imports and system calls are never paired. A pair is accepted only
when neither function has another candidate and it is corroborated: a pair whose only evidence is
`string` needs a second distinct such string, or any of `vtable`, `lua`, `bytes`, `callee` or
`anchor`. Every other candidate is written to the conflicts file, unresolved; a sole candidate that
is not corroborated is written there too, as an `uncorroborated` row. `data/anchors.tsv` holds function
pairs between images, each with its `verified_by` note. Anchors are always applied (naming `anchor` in `--evidence` is
an error): an anchor between the two images adds `anchor` evidence to the candidate it names, which
corroborates it, but never creates a candidate or resolves a conflict. `match` reports how the
anchors fared and fails when an accepted pair contradicts one.

Two checks reject a pair that the `callee` rule derives; candidates of every other evidence are
never rejected by them. A rejected pair is written to the conflicts file as a row whose side is the
reason, followed by the `image_a` function, then the `image_b` function with the rejected evidence
and both functions' `mhash`. It holds no `callee` evidence for the rest of the match, and stays a
candidate only while it has evidence other than `anchor`. A pair is contradicted by bytes when both
functions' hashes are non-empty and differ, the `image_a` function's hash is the hash of some
function of `image_b`, and the `image_b` function's hash is the hash of some function of `image_a`
(neither needs to be unique); this applies only between images analysed with the same Ghidra
language and only when `bytes` is chosen.

- `contradicted-by-bytes`: the derived pair is itself contradicted by bytes.
- `call-list-disagrees`: the derived pair's own call lists have the same length and do not agree at
  every position with the accepted pairs; two aligned direct callees that are contradicted by bytes
  also disagree. Call lists of different lengths are no evidence either way. Every pair holding
  `callee` evidence is re-tested each round against the pairs accepted then.

An accepted pair propagates its callees when its call lists have equal lengths and agree with the
accepted pairs; the bytes contradiction does not apply to that test.

Every function in a `<id>.fnsig.json` export must have a string `mhash` and `callees` and `strs`
arrays of strings, and every callee must be one of the forms above; anything else is an error
naming the export file and the function. `mhash` is the SHA-1 of the function's bytes with every
operand whose encoding holds a layout-dependent address zeroed: relative branch and call targets;
immediates, displacements and targets whose value is an address in the image; on PowerPC the high
half of an address in `addis`/`lis`, the low half of a `lis`-built address and, on PS3,
`r2`/TOC-relative operands. Registers-only operands, stack-frame offsets and field offsets are not
masked.

```bash
exemap derive x360-preview-profile --from "Mercenaries 2 Preview X360 (Jul 11 2008).iso" --out profile.pe_ghidra
exemap derive ps3-v103-na --from "UP0006-BLUS30056_00-MERCS2PATCHNA103-A0103-V0100-PE.pkg" --out eboot103.elf
```

`exemap translate <image> <address> --to <image> --matches <dir>` translates a function address
between two images through a directory of `match` outputs. Each pairs file (header
`<image_a>	<image_b>	evidence`) is an edge of the match graph, usable in both directions; a conflicts
file names no images and is not read, an image pair may have only one pairs file, and any other file
in the directory is an error. The address is mapped along every simple path between the two images
(the direct edge is one of them); a path answers when every hop has a pair, and stops at the first
function with none. The command prints every path and what it gives, then the answer when every
answering path agrees. It fails, listing each answer with its paths, when two paths disagree, and
fails as untranslatable when no path answers or no path exists.

`exemap coverage --matches <dir> --out <tsv> --contradictions <tsv>` translates every function of
every image in the graph (every function some pairs file names) to every other image. `--out` has
one row per image pair: functions, translated, direct (answered by the direct pair),
direct_confirmed (and by at least one composed path), composed_only, contradicted,
contradicted_direct and untranslated. `--contradictions` lists every contradicted translation with
each answer and the paths that gave it; two functions that compose to the same function along
different paths show up as a contradiction on the way back. The command fails when there is any
contradiction. Across the 28 match outputs of the eight PC, Xbox 360 and PS3 images there is no
contradiction: the v1.0 dump and the DRM-free v1.0 executable translate 23,619 functions, PC v1.0
and v1.1 22,124, PS3 v1.00 and v1.03 every one of 28,289, the Xbox 360 preview Final and retail
22,008 directly and the Profile image about 17,200–17,340 with each of them, PC and every Xbox 360
image about 2,790–2,800 (nearly all also confirmed through another image), PC and PS3 1,974
(1,700–1,706 directly, the rest through an Xbox 360 image), and Xbox 360 and PS3 about 1,990. The
Xbox 360 images are analysed with the Xenon language (see the notes repository's
`docs/xbox360_ghidra_xenon.md`).

The PC images' SecuROM layout is mapped by Ghidra scripts in the notes repository (see its
`docs/securom_splice_map.md`): `<id>.splices.tsv` lists every `.text` transfer into the SecuROM
blocks and how the code it reaches ends, and `<id>.securom_reach.tsv` labels every function that
starts in a SecuROM block by how `.text` reaches it.

### `dlc_port`
Incomplete Rust reimplementation of the Python DLC porter. Converts Xbox 360 DLC (RAR/STFS) to PC `vz-patch.wad`. Currently a work-in-progress; the Python version is still authoritative.

```bash
dlc_port --x360-rar Mercenaries.2.DLC.rar --source-wad vz.wad --output vz-patch.wad
```

## Building

### Prerequisites
- Rust 1.70+ ([rustup](https://rustup.rs/))

### Build all binaries
```bash
cargo build --release
```

Binaries land at `target/release/`:
- `qm` / `qm.exe`
- `wad_simulator` / `wad_simulator.exe`
- `ucfx_byteswap` / `ucfx_byteswap.exe`
- `loadprobe` / `loadprobe.exe`
- `dlc_port` / `dlc_port.exe`
- `exemap` / `exemap.exe`

### Build a single binary
```bash
cargo build --release -p ucfx_byteswap
```

## Testing

Tests run across the whole workspace with [cargo-nextest](https://nexte.st/):

```bash
cargo install cargo-nextest --locked   # once
cargo nextest run --workspace          # all crates
cargo test --workspace --doc           # doctests (nextest does not run these)
```

### Game-gated tests

Tests that read the retail game are **not** part of the run above. The game cannot be
committed, so they are built only by each crate's `retail` cargo feature, and one
command runs all of them:

```bash
scripts/find-vz-wad.sh --write   # once: writes the git-ignored .mercs2-local.toml
cargo xtask retail-test          # every game-gated test in the workspace
```

They find the game **only** through the repo-root `.mercs2-local.toml`; no
environment variable is consulted. The file holds one `key = "path"` per line:

| Key | Names | Read by |

`scripts/find-vz-wad.sh --write` writes `vz_wad` only, and rewrites the whole file, so
the console keys, `unpacked_exe`, `canonical_dir`, the console-image keys, the corpus keys and the tool keys are added by hand after it runs. The
tool keys (`rainbow_table` through `lua51_src_dir`) name files outside this repository; each
worktree reads them from its own config. When the file, a key a test needs,
or the file that key names is missing, the test fails with a message naming the file
and the key.
Two shapes exist: integration test targets declared
`required-features = ["retail"]`, and unit tests that need a crate's private items,
kept in src/ inside a `#[cfg(feature = "retail")] mod retail`. `cargo xtask
retail-test` selects both from `cargo metadata`; extra arguments go to
`cargo nextest run` (e.g. `cargo xtask retail-test --no-capture`). No game-gated test runs a game
executable or an installer: the PC builds and installs are read from the canonical tree and
checked by sha256.

CI runs on every pull request ([.github/workflows/ci.yml](.github/workflows/ci.yml)):
it runs the full workspace under nextest plus doctests (without the `retail` feature,
so no game-gated test is built there), and rolls the results up
into a per-crate pass/fail/skip table in the run's summary so a failure is
attributable to a specific crate.

## Crates

- **`mercs2_formats`** — Shared file-format parsing library (WAD, FFCS, ASET, PTHS, UCFX, etc.). Used by all other crates.
- **`wad_simulator`** — WAD consumption simulator binary.
- **`ucfx_byteswap`** — Xbox BE→PC LE converter (binary + library).
- **`dlc_port`** — DLC porter binary (work-in-progress).
- **`loadprobe`** — Log analyzer binary.
- **`mercs2_exemap`** — The cross-build exe map: the catalogue of known `Mercenaries2.exe` builds and dumps, their code layouts, the byte overlays that separate each build from its layout reference, and the `exemap` binary.
